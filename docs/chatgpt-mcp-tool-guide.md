# ChatGPT MCP tool discovery and recovery (BRC)

## What is grounded in the upstream project

The remote-desktop-commander repository is public integration documentation/manifests, not the hosted relay implementation: https://github.com/desktop-commander/remote-desktop-commander.
The linked open-source local implementation is https://github.com/wonderwhy-er/DesktopCommanderMCP. Its server.ts provides task-specific file/process tools, line/page offsets and tool schemas, and its config defines fileReadLineLimit/fileWriteLineLimit. BRC's stricter per-call write limits, recovery metadata and worker coordination are BRC-specific.

## Tool discovery profiles

BRC defaults to `BRC_MCP_TOOL_PROFILE=codemode`, with **14 advertised tools** on full-access connections, or **15** when operation recovery is enabled. The first tool is `code_mode`. It can search and invoke the permitted native agent methods and installed external MCP tools locally, so the model does not have to load the full catalog. Set `BRC_MCP_TOOL_PROFILE=core` to restore the previous 40-tool direct catalog (37 agent tools plus three relay tools). When durable `recover_operation` is enabled, it replaces the optional `list_sessions` entry to preserve the 40-tool maximum. Core omits the four skills-management entries from discovery; the admin skills interface is unaffected. `focused` and `full` remain available for extra specialized entries. Nineteen overlapping/deployment-specific tool entry points are retired from every profile. Set the variable on the **relay service**, redeploy and refresh the BRC MCP app's tool list in ChatGPT; the internal worker batch engine and compatibility handlers remain installed.

The Core profile covers safe single- and multi-file edits, searches, terminal commands, Git, actual project checks, background jobs, process recovery and installed external MCP plugins. `list_plugin_tools` and `call_plugin_tool` expose Computer Use, Playwright, Serena and MarkItDown without advertising their individual tools. Full restores specialized PDF, language and worker-coordination tools; retired duplicates and Docker-specific entries remain hidden. Profiles change discovery only, not access permissions. Android-only connections also filter by actual device capabilities.

Tool metadata is generated by `pnpm build && pnpm catalog:update && pnpm catalog:check`. The relay filters the bundled legacy catalog when devices are offline and still filters older online agents advertising retired names. Their handlers remain for compatibility with existing authenticated clients; new `tools/list` results contain no retired names. Online agents can supply supported newer input schemas. Do not rely on a live agent alone to refresh ChatGPT descriptions.

## Local JavaScript Code Mode for multi-step coding

Use `code_mode` when the AI needs several dependent file, Git, test or installed-plugin operations and only the final summary needs to return through MCP. The agent runs the provided JavaScript **function body** in a bounded QuickJS/WASM worker **on the paired device**. The guest has no direct Node.js modules, filesystem, process, network or browser globals; it can only call named BRC tools through `await tools.search(query)`, `await tools.describe(name)` and `await tools.call(name,args)`. These nested operations go through BRC's existing authorization, path validation, tool restrictions, source observations and receipts.

Example `code_mode` arguments:

```json
{
  "source": "const git = await tools.search('git'); const s = await tools.call('git_status', {path:'D:/projects/example'}); return {available:git.length, status:s.text.slice(0,600)};",
  "max_calls": 8,
  "max_runtime_ms": 30000
}
```

Always `await` tool calls. `tools.search(query)` returns ranked tool names; `tools.describe(name)` returns the exact JSON Schema and a bounded TypeScript call signature, without exposing all methods upfront. Use JavaScript loops, conditions, filtering and `try/catch` when necessary, but **do not blindly retry** uncertain mutations. A nested tool failure throws and normally stops remaining steps. Standard BRC permission checks apply even to calls made inside a workflow; Code Mode cannot silently install unapproved third-party MCPs. Calls to installed external plugins still pass through `list_plugin_tools`/`call_plugin_tool`.

Code Mode uses one remote MCP round trip for its workflow; each underlying file or tool action still happens locally and takes real time. Guest source is capped at 50,000 characters; default nested tool budget is 48 (maximum 96), with a default runtime limit of 85 seconds (maximum 105), bounded replies and a worker memory limit. For lengthy builds/tests, launch `spawn_job` from Code Mode and inspect the returned job ID with `get_job`/`wait_jobs` in later MCP calls. A pending job is not evidence of success. If guest code catches a nested tool failure, the result explicitly reports `status:completed_with_step_errors` and `allCallsSucceeded:false`. Prefer direct tools for simple reads or edits. Only the paired agent has the new sandbox; a relay-only update cannot run it on an older device agent.

### How BRC differs from Cloudflare's durable Code Mode

BRC follows the **one outer execution tool + local sandbox + progressive discovery + permission-checked tool bridge** pattern, rather than installing `@cloudflare/codemode` into the self-hosted relay. Cloudflare's optional durable runtime additionally maintains SQLite execution history, pauses for approval, deterministic replay, rollback hooks and owner-approved reusable snippets. Those capabilities are **not implemented in BRC's local Code Mode**. Instead BRC relies on its existing relay operation journal, bounded job tracking and plugin owner-approval process. An operation receipt is not an automatic replay or rollback of a multi-step script. Do not claim an entire workflow is durably resumable or atomic. See [Cloudflare's How Code Mode works](https://developers.cloudflare.com/agents/tools/codemode/how-it-works/).

### Docker and first activation

The relay Docker image defaults to `BRC_MCP_TOOL_PROFILE=codemode`, and `docker-compose.yml` also defaults to it (an existing `.env` or hosting environment can still override it). Build from the **full monorepo context** for local source changes. If an Easypanel/subfolder context omits the repository, supply a **pinned 40-character `GIT_SHA`** pointing to a remote commit containing these changes; the Dockerfile intentionally refuses a moving-branch fallback. Uncommitted local changes are not in a remote Git revision.

The relay container only advertises schemas and routes requests. **QuickJS/WASM Code Mode runs inside the paired agent**, so the agent must be rebuilt/restarted separately after active jobs have finished. The agent Dockerfile now includes its native build script and verifies its compiled Code Mode worker and QuickJS dependency. The relay image verifies Code Mode is present in its bundled catalog and set as default. After deploying, check `/health` (`mcpToolProfile: codemode`, `mcpTools: 15` when recovery is enabled), and refresh your ChatGPT MCP tool snapshot; the first advertised tool should be `code_mode`.

## Writing multiple files with the simplified MCP tools

The original shahidx0x/better-remote-commander has one `write_file` tool and one `read_multiple_files` tool, not a native public multi-file writer. BRC now follows this model: public clients use `write_file` and `edit_block`; the worker coordinator still uses its internal hash-checked batch engine where needed. Core keeps the reviewed `edit_files` and `apply_patch` for guarded multi-file source changes, but does not advertise the competing legacy `workspace_batch` editor.

For multiple new files, create required directories with `create_directory`, then call `write_file` **once per file**. Use `mode=rewrite` for a new file and `mode=append` only for a distinct next chunk. Confirm each result before moving to the next file; a successful chunk means only that specific chunk completed. The direct-write limits are 1 MiB of UTF-8 and up to 2,000 lines per call (new default: 1,000 lines).

For changes to existing source, use `read_code_file` for the current SHA-256, then `edit_block` with its optional hash precondition. After an uncertain network timeout, re-read the file and hash **before** retrying any write. Multiple sequential public writes are **not an all-or-nothing transaction**. A worker's internal batch integration is separate and still uses reviewed hashes.

## Which tools are in each profile

| Profile | Advertised agent tools | Best for |
| --- | ---: | --- |
| `codemode` (default) | 11 native direct tools + 3 relay = **14** (15 with recovery) | Code Mode-first coding/testing; nested tools discovered and invoked locally; lightweight direct fallback |
| `core` | 37 agent + 3 relay = **40 total** | Previous broad direct-tool catalog; handy for older agents or detailed troubleshooting |
| `focused` | 48 agent + 7 relay (+ optional recovery) | Extra debugging, management and worker coordination |
| `full` | 64 agent + 7 relay (+ optional recovery) | Specialized features, excluding 19 retired public entry points |

The optional relay `recover_operation` replaces Core's `list_sessions` when available, so the full-access Core listing remains 40. The 19 retired names stay callable by **legacy compatible agents** where explicitly authorized; new `tools/list` responses never advertise them. This avoids abruptly breaking cached MCP clients while removing duplicates from new tool discovery. This is not an authorization boundary. Refresh the custom MCP app's tool snapshot after relay redeploy.

## Agent and ChatGPT runtime sequence

1. Build the BRC code (`pnpm build`), then redeploy the **relay**. The relay serves the stable MCP descriptions, schemas and global instructions.
2. Restart the **agent** from BRC Agent shortcut after current jobs finish. New agent code does not replace an already-running process; RAM-only worker plans are lost at restart.
3. From ChatGPT Plugins, open the installed custom BRC plugin's settings/details and use **Refresh** to retrieve updated tools, descriptions and server instructions. Workspace admins/owners with permission can refresh action definitions in workspace app settings. Review changes and enabled actions. This is **not** the same as re-authorizing OAuth.
4. Start a new conversation or reselect the plugin if the current chat still shows old tool definitions. Reconnect/reauthorize only if the app reports an expired/broken account connection or Refresh is unavailable/unsuccessful.
5. Verify a short read (`list_devices` if more than one device; then `read_file`) and a safe `read_multiple_files` call. Validate `run_command` exit code rather than merely seeing a started process.

Current ChatGPT documentation: https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt and https://developers.openai.com/api/docs/guides/custom-mcp-server.

## Model-facing tool-selection contract

- Multi-step coding -> `code_mode` with `await tools.search`, `await tools.describe`, and `await tools.call` to reduce MCP round trips; validate nested results and use durable jobs for long work. Direct file tools remain better for one short action.
- Known ONE file -> `read_file` with bounded line offset/length. Known TWO OR MORE files -> `read_multiple_files`. Unknown filenames -> `start_search` (`wait=true`), then read the actual matches.
- For large text, follow `structuredContent.read.next` / `structuredContent.batch.continuations`. If a giant line is clipped, use `read_code_file({path,charOffset,charLength})` and its `nextCharOffset` until null. PDF reads count PAGES, default 3, max 5; batch reads up to 2 pages per PDF.
- For focused edits, read current source/hash then use `edit_block` with `expected_sha256`. For multiple files, use **separate** `write_file`/`edit_block` calls, verifying each result; do not assume an all-or-nothing multi-file transaction exists. Worker integration still uses internal hash-checked batch commits.
- `write_file` uses explicit `mode=rewrite` for replacement and `mode=append` for continuation. It rejects >1MiB or >configured line limit per call before mutation. A successful result confirms ONLY the requested chunk, not a whole generated artifact. Re-read and compare after transport errors or timeouts before retrying any write; append is not idempotent.
- One-shot commands -> `run_command` with real exit codes. Long-running sessions -> `start_process`, then `read_process_output`; PID means started, not finished. Many independent tasks -> `run_parallel`, default 4 and max 8; never concurrently mutate the same path. Follow `wait_jobs(group)` or `get_job(step_offset)` on truncated job replies, not rerun commands.
- BRC worker tools coordinate staged patches, not real independent LLMs. Use `worker_tasks` only if the AI host can spawn actual subagents; claim, renew lease, submit `worker_patch`, then coordinator `worker_integrate` preview/apply/verify.
- Errors: inspect `structuredContent.error.code` and optional `recovery.suggestion`. BUSY means wait/reduce concurrency; FILE_CONFLICT means reread hashes; CHECK_FAILED means real verification failed; RESULT_TOO_LARGE means result exceeded the 512 KiB agent/relay forwarding budget or encoding failed, and a mutation may already have completed. Never blindly repeat a mutation. An independent ChatGPT or network stream error can still occur.

## Boundaries

No MCP wrapper can guarantee ChatGPT never shows 'Error in message stream'. BRC limits per-tool responses and combined jobs to reduce one class of overload. Network resets, stale OAuth/app snapshots, and platform-side stream failures remain possible. If a host stream fails during a mutation, verify the file/operation first.
